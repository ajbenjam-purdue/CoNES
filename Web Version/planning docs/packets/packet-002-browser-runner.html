Packet 002

Browser Runner Implementation

This packet moves the project from WASM feasibility into the first browser-visible implementation. The target is a minimal static runner that first loads the packaged CoNES runtime data, then uploads one .cnes file, invokes the proven modular CoNES WASM runtime inside a worker, displays captured JSON, and offers a downloadable result.

Accepted by human review Gate 1 passed in Node Gate 2 passed in Chrome Binary tables packaged Implementation packet No full IDE yet Packet 003 next

Context

What Is Proven

The existing CLI-shaped CoNES source compiled to a modular Emscripten runtime. Node-hosted probes successfully ran unit, include, and material-dependent scripts through callMain(). The existing material tables have now been copied into a static runtime-data package for browser loading.

What Is Not Proven

Gate 2 proves browser execution in Chrome automation, and the current runner has now passed human acceptance for the intended Packet 002 behavior. What remains is productizing the proof inside the Vite/React application shell without losing the raw stdout/stderr contract.

Packet 002 prerequisite resolved

The worker should use the manifests at /runtime-data/materials/manifest.json and /runtime-data/libs/manifest.json to fetch static assets and write them to their declared vfsPath values before invoking CoNES. Each fetched file should match the manifest's bytes and sha256 before it is mounted.

Goal

Upload

User selects one local .cnes file.

Assets

Worker loads manifests and mounts runtime data.

Prepare

Worker writes upload to /work/input.cnes.

Run

Worker calls callMain(["/work/input.cnes", "--json"]).

Export

UI displays stdout JSON and downloads a JSON file.

Workstreams

Worker Runtime

Critical path
  • Create a browser worker that imports the Emscripten factory.
  • Use locateFile so .wasm resolves from the intended runtime path.
  • Create the module with thisProgram: "/app/cnes" so CoNES resolves executable-relative assets under /app.
  • Create /app, /app/materials, /app/libs, and /work before loading runtime data.
  • Fetch material and lib manifests, verify bytes and sha256, then write every listed file to its declared vfsPath.
  • Capture stdout and stderr separately with worker responses.

Runner UI

Keep it minimal
  • Add one file input for .cnes files.
  • Add run, reset, status, stdout, stderr, and download regions.
  • Show JSON parse status without replacing raw stdout as the source of truth.
  • Avoid editor, autocomplete, project tree, accounts, server calls, or examples-first flow.

Runtime Assets

Static only
  • Place generated cnes-module.js and cnes-module.wasm where the worker can fetch them over HTTP.
  • Use packaged static materials from public/runtime-data/materials, not an empty-directory workaround.
  • Use packaged static libraries from public/runtime-data/libs.
  • Verify the worker can fetch all manifest-listed files over HTTP before the solve starts.

Worker Contract

Request:
{
  type: "run",
  requestId: string,
  file: {
    name: string,
    size: number,

    bytes: ArrayBuffer

{
  type: "success",
  requestId: string,
  exitCode: 0,
  stdout: string,
  stderr: string,
  parsedJson?: unknown,
  timings: { wallMs: number }
}

{

  requestId: string,

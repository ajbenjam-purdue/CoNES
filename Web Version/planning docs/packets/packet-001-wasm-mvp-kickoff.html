Mission

Non-Negotiables

  • The first MVP is all client-side and deployable as static assets on Vercel.
  • The first interface uses user upload for an existing .cnes file. Do not hide behind bundled examples.
  • The first result format is captured cnes --json output.
  • The CoNES C++ core is not refactored in this packet. Agents may propose wrapper-only adapters or build shims.
  • The solver must run in a Web Worker or equivalent isolation path so browser UI remains responsive.
  • Any change that weakens native CLI behavior must be flagged before implementation.

Lane Closeouts

Lane A: Emscripten Compile Probe

Status: passed after toolchain install
  • Initial finding: em++ and emcc were absent locally.
  • Emscripten 5.0.7 was installed with Homebrew.
  • Default Emscripten cache path was blocked, so probes used EM_CACHE=/private/tmp/emscripten-cache.
  • Compile succeeded with -I . -I /opt/homebrew/include/eigen3; README's project-root Eigen assumption is not true locally.
Evidence

Generated /private/tmp/cnes-wasm-probe/cnes-module.js and /private/tmp/cnes-wasm-probe/cnes-module.wasm. No C++ core refactor was required for the proof.

Lane B: CLI Invocation Wrapper

Status: validated in Node-hosted runtime
  • Use a modular Emscripten factory with INVOKE_RUN=0.
  • Invoke the existing CLI contract through module.callMain(["/work/input.cnes", "--json"]).
  • Capture stdout with print and stderr with printErr.
  • Prefer a fresh module instance per solver run for the MVP until same-instance reuse is proven.
Risk carried forward

The JSON writer is manual and some error strings may not be escaped perfectly. Packet 002 should preserve raw stdout and stderr so failures remain inspectable.

Lane C: Virtual Filesystem And Assets

Status: validated by native and WASM probes
  • Use virtual executable path /app/cnes so executable-relative assets resolve under /app.
  • Write the uploaded MVP script to /work/input.cnes.
  • Mount bundled standard libraries under /app/libs.
  • Create /app/materials before invoking main, even if empty.
Important behavior

If /app/materials is missing, CoNES attempts the Python build_substances() fallback and pollutes stdout. Empty /app/materials is acceptable for ideal-gas cases.

Lane D: Minimal Browser Runner

Status: ready for Packet 002 implementation
  • Component plan: RunnerPage, FilePicker, RunControls, StatusPanel, OutputPanel, and DownloadJsonButton.
  • Worker messages should carry requestId, input metadata, stdout, stderr, exit code, parsed JSON, and timings.
  • UI states include no file, uploading, runtime loading, running, success, JSON parse warning, solver failure, and worker load failure.
  • Full IDE, autocomplete, project tree, multi-file upload, and polished result tables should wait.
Implementation implication

Packet 002 should implement a runner, not an IDE. Raw stdout JSON remains the source of truth.

Lane E: Native Parity Harness

Status: test matrix ready
  • Tiny valid case: tests/test_units.cnes, expecting Power=50, T2=298.15, and v_copy=10.
  • Normal example: examples/Brayton_Cycle_example.cnes, expecting eta=0.3685210678.
  • Include case: examples/test.cnes, expecting T_surface=40 when heat_transfer_lib.cnes is mounted.
  • Material case: examples/HVAC_example.cnes, expecting COP_HP=11.7950669027 when all 240 material tables are mounted.
Comparison rule

Compare parsed JSON, not raw text. Ignore timing fields. Classify mismatches as numerical drift, structural JSON, runtime failure, or unsupported browser filesystem behavior.

Lane F: Vercel Static Deployment Probe

Status: deployment plan ready
  • Use static paths for frontend assets, worker, Emscripten glue, WASM binary, materials, libs, and planning docs.
  • Serve .wasm as application/wasm and .cnesbin as application/octet-stream.
  • Use immutable caching for content-hashed runtime files; use versioned or manifest-managed material tables.
  • Do not add Vercel serverless functions, API routes, or backend solve endpoints for the MVP.
Production warning

Local file:// testing is not representative. Worker imports, fetches, WASM MIME behavior, and binary assets must be tested over HTTP.

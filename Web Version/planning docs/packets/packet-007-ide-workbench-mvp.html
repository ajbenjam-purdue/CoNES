Packet 007

IDE Workbench MVP

Packet 007 closes the first real IDE loop: edit current CoNES source, run that exact source from the browser, inspect structured results, and keep raw stdout/stderr available. This packet connects authoring and execution without changing the CoNES C++ core or introducing a backend.

Human accepted Deployed IDE experience Monaco required Run from editor buffer Raw output preserved Client-only No C++ refactor

Goal

User Outcome

A user can open or create a .cnes file, edit it, run the current editor contents, and inspect results without re-uploading the same file through a separate Runner workflow.

Product Outcome

The Web Version begins to feel like a CoNES workbench: source on one side, run controls and results nearby, and operational tooling visible without marketing-style framing.

Engineering Outcome

Editor source, worker execution, structured results, raw artifacts, and downloads share one contract. Existing Runner behavior remains valid.

Boundary

This is not a linter, diagnostics engine, multi-file project system, or CoNES language server. Those should land after the edit-run-results loop is stable.

Implementation Companion

Build guide

The opinionated implementation companion for this packet is Packet 007 Companion: IDE Workbench Implementation Guide. It names the expected files, dependency step, Monaco component, runtime helper, route wiring, and browser smoke shape.

Success Metrics

  • Open or create a .cnes file in the IDE workbench.
  • Edit source text in Monaco with line numbers and keep dirty state visible.
  • Click Run from the workbench and execute the current editor buffer.
  • Update structured results, raw stdout, stderr, exit code, and JSON download from that buffer.
  • Runtime prewarm still reaches ready before file selection or first run.
  • Raw output is secondary: success cases keep it quiet, failure cases open Diagnostics.

Implementation Lanes

Lane Owns Do Not Touch
Workbench layout A route-backed IDE page with editor, run controls, result pane, and raw output pane. Do not replace the Runner route or remove existing Tools visibility.
Shared source state Current file name, source contents, dirty state, loaded source snapshot, and download behavior. Do not introduce browser storage, project folders, or multi-file include behavior in this packet.
Run current buffer A source-text run path that sends the current buffer through the existing worker client. Do not change callMain(["/work/input.cnes", "--json"]) or the worker result contract.
Results integration Reuse the Packet 005 structured result viewer and preserve raw stdout/stderr. Do not parse around CoNES JSON in a way that hides raw output or changes failure semantics.
Editor engine Install and integrate Monaco as the source editor for the workbench. Do not add diagnostics, completion, syntax validation, or language-server assumptions yet.

Workbench should compose existing editor, runner, results, and runtime pieces where practical. If extraction is needed, extract small source-state and run-result helpers rather than rewriting current feature pages.

Contracts To Preserve

Runtime contract

Continue using thisProgram: "/app/cnes", mounted /runtime-data, and callMain(["/work/input.cnes", "--json"]). The workbench changes where contents come from, not how CoNES is invoked.

Output contract

Structured results are primary. Raw stdout/stderr remain preserved and inspectable under Raw output, with stdout labeled Output and stderr labeled Diagnostics.

Monaco contract

Monaco is a core part of this packet. Use it for the source editor, line numbers, selection behavior, and the first IDE-quality editing surface. Diagnostics, completion, semantic highlighting, and language-server behavior remain out of scope.

Risks And Decisions

Question Default Answer Review Trigger
Should Workbench replace Runner as the first screen? Yes. Human review accepted Workbench as the primary experience. Completed in the focused IDE pass.
Should Monaco ship in this packet? Yes. Monaco is required for the IDE Workbench MVP. If integration creates build or worker conflicts, fix the integration rather than falling back to textarea.
Should edited source be persisted automatically? No. Keep explicit download/save behavior. A later project-files packet defines browser storage and workspace persistence.
Should lint diagnostics be attached to the editor? Yes, but manual lint comes first. Packet 008A defines the diagnostic contract; Packet 008B adds debounced auto lint.

Packet 004

Runtime Hardening

Packet 004 makes the accepted client-side CoNES runtime easier to inspect, diagnose, and trust before the project adds editor, linter, multi-file, or richer results workflows. The runtime contract stays stable; this packet improves metadata, error reporting, status visibility, and verification coverage around that contract.

Context

Vercel Interrupt Resolved

Packet 004A established the new Git origin, Vercel automatic deployments, and public test URL first. Runtime hardening can now use both local and hosted deployments for verification. The public reviewer target is https://cones-web-version.vercel.app/runner/.

Packet 004 Reminder

Packet 004 is not the editor, linter, or richer results phase. It is the runtime trust phase: metadata, stable diagnostics, Tools status, cache policy, and verification expansion before larger IDE layers depend on the worker.

Accepted Baseline

Packet 002 proved the browser worker runtime and Packet 003 moved it into a Vite, React, Tailwind v4, and shadcn-compatible app shell. Human verification confirmed that selecting a .cnes file in the React runner works as intended.

Implemented Result

The runtime now has generated metadata, checksum verification, stable diagnostic codes, a Tools runtime status page, last-run timing visibility, and browser verification for positive and negative paths.

Preserved Contract

Do not change the runtime surface casually

Packet 004 may add metadata and diagnostics, but the accepted solve path remains /runtime/cnes-worker.js, /runtime-data, thisProgram: "/app/cnes", and callMain(["/work/input.cnes", "--json"]). 

Accepted run path:
React Runner
  -> CoNESWorkerClient
  -> /runtime/cnes-worker.js
  -> /runtime/cnes-module.js + /runtime/cnes-module.wasm
  -> /runtime-data/materials/manifest.json
  -> /runtime-data/libs/manifest.json
  -> /work/input.cnes
  -> callMain(["/work/input.cnes", "--json"])
  -> raw stdout/stderr returned to UI

Implementation Results

Metadata

npm run generate:runtime-metadata writes public/runtime/runtime-metadata.json with runtime artifact bytes, sha256 values, manifest summaries, the WASM build command, and the preserved thisProgram: "/app/cnes" contract.

Diagnostics

Worker and client failures now use a stable diagnostic taxonomy including module load, module init, WASM load, manifest fetch, manifest invalid, byte mismatch, sha256 mismatch, missing file, unsupported message, invalid worker response, and nonzero CoNES exit.

Tools Status

The Tools route now reads /runtime/runtime-metadata.json and shows worker paths, artifact checksums, runtime-data manifest counts, mount roots, accepted invocation arguments, and locally stored last-run timings.

Verification

Local verification passed with npm run verify:runtime-metadata, npm run verify:runtime-data, npm run build, and npm run verify:browser against http://127.0.0.1:4173/runner/.

Workstreams

1. Runtime Metadata

Build facts
  • Add a static runtime metadata file under public/runtime or public/runtime-data.
  • Record CoNES version, Emscripten version if available, build command, artifact byte counts, and sha256 for cnes-module.js and cnes-module.wasm.
  • Record material and library manifest summaries: counts, total bytes, and manifest sha256.

2. Worker Error Taxonomy

Diagnosable failures
  • Normalize worker errors into stable codes for module load, WASM load, manifest fetch, byte mismatch, sha256 mismatch, missing file, unsupported message, invalid worker response, and CoNES nonzero exit.
  • Keep stdout and stderr visible separately for failures.
  • Do not mask the raw CoNES JSON error output; surface diagnostics as an additional layer.

3. Tools Runtime Status

User-visible inspection
  • Replace the Tools placeholder with a runtime status page.
  • Show worker path, module paths, runtime-data paths, artifact sizes, manifest counts, checksums, and accepted invocation arguments.
  • Show last-run timings from the worker when available: module load, runtime-data mount, solve, and wall time.

4. Fetch And Cache Policy

Explicit behavior
  • Document current behavior: runtime data is fetched and verified per worker run.
  • Decide whether Packet 004 keeps per-run verification or introduces session-level worker/runtime-data reuse.
  • If caching changes, keep checksum verification and make invalidation explicit.

5. Verification Expansion

Negative paths
  • Keep npm run build, npm run verify:runtime-data, and npm run verify:browser passing.
  • Add at least one negative-path verification for missing manifest, checksum mismatch, or worker response validation if feasible without destabilizing the app.
  • Update verification notes with the exact commands and observed results.

Scope Boundaries

In scope

Runtime metadata, worker diagnostics, Tools runtime status, explicit cache policy, and verification improvements.

Out of scope

Monaco editor, lint UI, result tables, multi-file projects, changing Vercel project ownership/settings, backend solve APIs, and C++ solver refactors.

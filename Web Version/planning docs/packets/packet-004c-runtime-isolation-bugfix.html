Packet 004C

Runtime Isolation Bug Fix

This packet designs the fix for a first-run and file-order-dependent runtime symptom observed after Packet 004B. The goal is to keep the optimistic prewarm experience while restoring native CLI-style isolation for each solve.

Bug design State isolation After Packet 004B No solver refactor No backend Preserve prewarm UX

Problem Statement

Symptom

After a fresh app start, test.cnes can fail on the first browser run while HVAC_example.cnes succeeds. After at least one successful run, subsequent runs appear normal. The user cannot tell from the UI whether this is a solver failure, runtime initialization failure, stale state, or file handling issue.

Known Non-Symptom

modularity_usage.cnes fails natively with NewtonSolver: Failed to converge after 5 attempts.. That case is a valid CoNES solver-level failure, not evidence of browser runtime corruption.

Expected Behavior

A browser run should match a native CLI process run for the same input. A failed solve must not influence the next solve, and the first solve after prewarm must not behave differently from later solves.

User-Facing Clarity

The UI currently reports JSON Parsed even when parsed JSON contains "success": false. The fix should distinguish valid solver failure JSON from successful solve JSON.

Likely Source

Current prewarm reuses one mutable Emscripten module across solves

Packet 004B changed the runtime from process-like execution to a long-lived browser Worker that keeps one initialized CoNES module alive. That reduces run latency, but it also means C++ static state, virtual filesystem state, global parser/solver state, stdout hooks, and Emscripten runtime state can survive between solves. 

Current Packet 004B flow:
App load
  -> create one Worker
  -> create one Emscripten CoNES module
  -> mount /app/materials and /app/libs once
  -> keep module alive

Every run
  -> overwrite /work/input.cnes
  -> callMain(["/work/input.cnes", "--json"]) again on the same module
  -> reuse the same module for later files
Native parity mismatch

Native CoNES execution is process-shaped: each CLI invocation starts from a fresh process. Repeated callMain() inside one Emscripten module is not the same contract unless the C++ program is explicitly designed and tested for reentrant in-process execution.

Technical Explanation

Mutable Module State

The Emscripten module owns memory, filesystem state, runtime hooks, and loaded program state. Calling callMain() repeatedly can leave data behind even when /work/input.cnes is overwritten.

CoNES Is CLI-Shaped

The approved web boundary says to wrap CoNES/src/main.cpp, not refactor the solver. Therefore the browser wrapper should emulate a new process per solve as closely as possible.

Prewarm Still Matters

The expensive browser work is mostly fetching WASM and runtime-data. We can prewarm those bytes without reusing the same mutable C++ module for every solve.

Fix Design

Prewarm bytes, isolate solves

Keep the optimistic startup behavior, but redefine prewarm as asset preparation rather than reusable solver-module preparation. Each Run should create a fresh CoNES module, mount already-fetched runtime-data bytes, call main once, return output, and discard the module. 

Proposed Packet 004C flow:
App load
  -> Worker starts
  -> import cnes-module.js factory
  -> fetch cnes-module.wasm via browser cache / Emscripten locateFile
  -> fetch manifests
  -> fetch, verify, and store runtime-data bytes in Worker memory
  -> Tools reports Runtime assets ready

Every run
  -> create a fresh Emscripten module instance
  -> create /app and /work directories
  -> mount cached runtime-data bytes into the fresh module FS
  -> write uploaded file to /work/input.cnes
  -> callMain(["/work/input.cnes", "--json"]) exactly once
  -> return stdout/stderr/timings
  -> release module reference

Implementation Plan

1. Rename Runtime State

Make status honest
  • Change user-facing copy from Runtime ready to Runtime assets ready if the module is no longer kept alive.
  • Keep the existing idle, preparing, ready, and failed lifecycle unless a clearer name is needed.

2. Cache Verified Runtime Data

Worker-owned bytes
  • During prewarm, fetch manifests and every listed runtime-data file.
  • Verify byte counts and sha256 during prewarm.
  • Store immutable records such as { vfsPath, bytes } in Worker memory.

3. Fresh Module Per Run

Process-like execution
  • On each run, call the Emscripten factory to create a fresh module instance.
  • Mount cached runtime-data bytes into that fresh instance.
  • Call callMain(["/work/input.cnes", "--json"]) once, then drop the module reference.

4. Clarify Solver Failure JSON

Readable state
  • If stdout parses and parsedJson.success === false, show Solver failed instead of JSON Parsed.
  • Surface parsedJson.error in the side panel without hiding stdout.

Payload Notes

Current Build Size

Current dist is about 3.9M on disk. Runtime assets are about 752K, with cnes-module.wasm around 650K raw and roughly 247K gzipped.

Runtime Data Size

Runtime data is about 2.13 MiB actual bytes across 244 files. Materials account for 240 small files and about 2.06 MiB. Gzipped file-by-file size is about 1.74 MiB.

Implication

The total payload is acceptable for an MVP, but many small material requests make prewarm chatty. This packet does not require bundling material files, but future work may package runtime-data into fewer static archives.

Do Not Optimize Prematurely

Fix correctness and state isolation before compressing or repacking runtime-data. A smaller corrupt runtime is not a better runtime.

Agent Directive

Implementation boundary

Do not refactor CoNES C++ or change the JSON contract. The owned work is the browser wrapper, Worker lifecycle, runtime-data caching strategy, UI labeling, and verification.

  • Read this packet, Packet 004B, public/runtime/cnes-worker.js, worker-client.ts, and runtime-prewarm.ts before editing.
  • Preserve thisProgram: "/app/cnes", /runtime, /runtime-data, and callMain(["/work/input.cnes", "--json"]).
  • Keep local-first static deployment. Do not introduce a backend, queue, server action, database, auth, Railway, or Redis.
  • Extend browser verification to cover first-run test.cnes after a fresh page load and failure-then-success ordering.

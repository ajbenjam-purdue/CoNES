CoNES Web Version

Client-Side Application Brief

This document frames the first browser-based CoNES milestone: a static Vercel-deployed web app that accepts a local .cnes upload, runs the existing CLI-shaped CoNES engine through WebAssembly, captures --json output, and provides a downloadable result file.

Intent

Product Direction

CoNES Studio should feel like a browser IDE for CoNES while preserving the proven local runtime. The product should make one active .cnes buffer easy to author, lint, run, inspect, rename, and export without pretending to be a cloud workspace or project file manager.

MVP Boundary

The current app should stay intentionally focused: open or draft one .cnes file in the Monaco Workbench, rename the active buffer, lint it, run it, inspect structured results, and download source or JSON. Raw output, runtime internals, Tools, Docs, and Workspace remain development/debug surfaces behind the hard-coded flag. Autocomplete and real project workspaces remain later work.

Gate Results

WASM feasibility is proven for the current CLI-shaped program

Emscripten 5.0.7 was installed locally. The existing CoNES/src/main.cpp compiled to WebAssembly without a C++ core refactor when built with the Eigen include path. Gate 1 proved the modular runtime in Node. Packet 002 then proved browser Worker execution in Chrome and passed human acceptance for upload, run, stdout/stderr, and JSON download behavior.

Compile Result

Generated cnes-module.js and cnes-module.wasm under /private/tmp/cnes-wasm-probe. The WASM binary was about 531K.

Runtime Result

The wrapper created /app/materials, /app/libs, and /work/input.cnes, then invoked callMain(["/work/input.cnes", "--json"]).

Behavior Result

The probes returned valid JSON for unit, include, and material-dependent scripts, including Power = 50 W, T_surface = 40 C, and COP_HP = 11.7950669027. 

env EM_CACHE=/private/tmp/emscripten-cache em++ -O2 -std=c++20 \
  -I . -I /opt/homebrew/include/eigen3 \
  src/main.cpp \
  -o /private/tmp/cnes-wasm-probe/cnes-module.js \
  -sMODULARIZE=1 \
  -sEXPORT_NAME=createCoNESModule \
  -sENVIRONMENT=worker,node \
  -sINVOKE_RUN=0 \
  -sEXPORTED_RUNTIME_METHODS=FS,callMain \
  -sALLOW_MEMORY_GROWTH=1
Confirmed wrapper requirement

The runtime must set thisProgram: "/app/cnes" and create or mount /app/materials before invoking main. If the materials directory is missing, CoNES attempts the Python substance-building fallback and pollutes stdout.

Runtime Data Status

Packaged Assets

The existing binary material tables and standard library files have been copied into Web Version/public/runtime-data. This makes runtime data a first-class static asset set for the browser worker, not a later workaround.

Mount Contract

Manifests declare the browser URL and target virtual filesystem path for each asset. The worker should load /runtime-data/materials/manifest.json and /runtime-data/libs/manifest.json, then write every listed file before calling CoNES. Entries include bytes and sha256 for integrity checks.

Runtime Artifact Contract

Proof Location

The first successful modular WASM artifacts were generated under /private/tmp/cnes-wasm-probe. That location is proof-only and should not be the browser runner's dependency.

Packet 002 Location

Packet 002 builds cnes-module.js and cnes-module.wasm into Web Version/public/runtime, then loads them from the browser worker over HTTP. Packet 003 should keep these paths stable while migrating the UI to Vite, React, Tailwind v4, and shadcn/ui.

Target Architecture

Step 1

User uploads an existing .cnes file.

Step 2

The browser writes the file into the WASM virtual filesystem.

Step 3

A Web Worker invokes the wrapped CLI with input.cnes --json.

Step 4

The worker captures stdout and returns JSON to the UI.

Step 5

The UI offers a downloadable JSON result file.

Vercel static assets
  -> browser UI
  -> Web Worker
  -> Emscripten-generated CoNES runtime
  -> virtual filesystem
  -> captured stdout JSON
  -> downloadable result

Known Constraints

No Core Refactor

The C++ engine should be treated as an existing CLI-shaped program. The web experiment should wrap it rather than extracting a new library API.

No Server Runtime

Vercel should host static files only for the MVP. Solver execution happens in the user's browser, not in Railway, Redis workers, or serverless functions.

Uploaded Input First

The first test should not depend on bundled example scripts. The user should choose an existing local .cnes file.

WASM Questions To Answer First

  1. Can the current C++20 source compile with Emscripten without changing the core solver architecture?
  2. Does Emscripten support the current use of std::format in the selected compiler/runtime configuration?
  3. Can std::filesystem operations be mapped to the virtual filesystem cleanly enough for input files, includes, libs, and materials?
  4. Can stdout be captured reliably when invoking the CLI-shaped entry point from JavaScript?
  5. Does the runtime behave predictably when materials/ is missing, bundled, or lazy-loaded?
  6. How should uploaded scripts with include dependencies be handled in a single-file MVP?
Planning limit

Because the core cannot be refactored, the plan must accept some awkwardness around simulating files and arguments. A clean library-style API can remain a future recommendation, but it is not part of the first implementation path.

Risk Register

Risk Why It Matters Early Test
C++20 support gaps The current CLI may rely on standard library features that are not smooth in the WASM toolchain. Run the compile probe before building interface code.
Filesystem assumptions The CLI expects paths, executable-relative materials, and normal file reads. Mount uploaded files and static assets into the virtual filesystem.
Single-file upload limits Scripts using include may fail if dependencies are not uploaded or pre-mounted. Document MVP limitations and add multi-file upload later.
Runtime size The browser must download WASM glue, runtime code, and material data. Measure first-load size after the initial Emscripten build.

Definition Of MVP Success

Functional success

A user can open the deployed page, upload a local .cnes file, run it entirely in-browser, see whether execution succeeded, and download the captured --json output.

Technical success

The team understands the remaining blockers for materials, includes, browser compatibility, and future IDE features based on a working WASM execution path rather than speculation.

Web Version Engineering Checklist

This checklist translates the browser-only plan into concrete engineering work. It assumes a static Vercel deployment, local browser execution, Monaco-backed .cnes authoring, wrapped CLI behavior, and downloadable --json results.

Fixed Decisions

  • The planning docs live under Web Version/planning docs.
  • The accepted Workbench can open an existing .cnes file or draft a new one in Monaco.
  • The C++ core is not refactored for the first roadmap; the CLI-shaped entry point is wrapped.
  • The first downloadable result format is the existing cnes --json output.
  • The app shell will use Vite, React, TypeScript, Tailwind CSS v4, and shadcn/ui.
Decision boundary

If wrapping the CLI becomes impossible without changing core source structure, that result should be recorded as a feasibility finding. The next decision would be whether to permit a narrow adapter layer or defer browser-only execution.

Phase 0: Emscripten Compile Probe

Goal

Answer whether the current CLI can become WASM
  • Install or locate an Emscripten toolchain in the development environment.
  • Compile src/main.cpp with -std=c++20, project includes, and Eigen from /opt/homebrew/include/eigen3.
  • Build a modular runtime with MODULARIZE, INVOKE_RUN=0, FS, and callMain.
  • Run unit, include, and material-dependent probes through the WASM runtime.
Working modular probe:
env EM_CACHE=/private/tmp/emscripten-cache em++ -O2 -std=c++20 \
  -I . -I /opt/homebrew/include/eigen3 \
  src/main.cpp \
  -o /private/tmp/cnes-wasm-probe/cnes-module.js \
  -sMODULARIZE=1 \
  -sEXPORT_NAME=createCoNESModule \
  -sENVIRONMENT=worker,node \
  -sINVOKE_RUN=0 \
  -sEXPORTED_RUNTIME_METHODS=FS,callMain \
  -sALLOW_MEMORY_GROWTH=1

Phase 1: Minimal Browser Runner

Interface Tasks

Keep it plain
  • Create a static page with a file input restricted to .cnes.
  • Add a run button with disabled, running, success, and failure states.
  • Render captured JSON text in a readable output region.
  • Create a download control for the JSON result blob.

Runtime Tasks

Worker-owned execution
  • Load the Emscripten-generated runtime inside a Web Worker.
  • Write uploaded file contents to a known virtual path such as /work/input.cnes.
  • Invoke the wrapped program with arguments equivalent to /work/input.cnes --json.
  • Capture stdout and stderr separately so failures are diagnosable.

Phase 2: Filesystem And Assets

Area Task Success Criteria
Materials Load the packaged material manifest and mount every listed .cnesbin file. Tabulated substance cases succeed without a special developer-only copy step.
Includes Document how single-file upload behaves when a script contains include. The MVP either reports a clear include failure or supports a planned multi-file upload path.
Libraries Evaluate whether libs/ should be pre-mounted from static assets. Common library includes can be made available without server execution.
Storage Decide whether material tables should be bundled, fetched on demand, or cached in browser storage. The chosen strategy has acceptable startup size and predictable offline behavior.

Phase 3: Minimal IDE Shell

Editor

Add a browser editor only after the upload runner works. Start with file contents loaded into the editor, then run from editor text.

Lint

Reuse the same WASM runtime to invoke lint-style arguments. Surface line errors only after stdout and stderr are stable.

Results

Keep raw JSON download as the source of truth. A formatted table can be a convenience layer once result shape is confirmed.

Verification Plan

  1. Run one simple uploaded script that does not require material tables.
  2. Run one uploaded script that requires a known material table.
  3. Run one intentionally invalid script and confirm useful failure output.
  4. Run one script with an include statement and record MVP behavior.
  5. Compare WASM JSON output against native CLI JSON output for the same input file.
  6. Run browser verification against https://cones-web-version.vercel.app/runner/ after pushed changes deploy.

Open Decisions

Wrapper tolerance

How much wrapper code is acceptable if the current CLI needs a browser-specific invocation layer around it?

Multi-file project handling

Should the post-MVP workflow accept folders, multiple uploads, or an in-browser project filesystem?

Materials delivery

Should tabulated materials be loaded eagerly for reliability or lazily for faster page startup?

Native parity

What level of byte-for-byte or value-level parity is required before the browser version is considered credible?

MVP Done Criteria

  • Static app loads from a Vercel deployment without backend services.
  • User can upload a local .cnes file.
  • Uploaded input is written into the WASM virtual filesystem.
  • Wrapped CoNES CLI executes with --json semantics.
  • stdout JSON is displayed or clearly surfaced in the browser.
  • JSON result can be downloaded as a file.
  • Failure output is captured without freezing the browser tab.
  • Remaining blockers for materials and includes are documented from real tests.
